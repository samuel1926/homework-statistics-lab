02 / TECHNICAL FOUNDATIONS

Six primitives. Six distinct jobs.

These mechanisms complement one another; no single algorithm substitutes for all of them.

01 / BIP-39

Words → binary seed

High-quality random entropy is encoded into a human-readable mnemonic with checksum bits. PBKDF2-HMAC-SHA512 converts the normalized mnemonic plus optional passphrase to a 64-byte seed using 2048 iterations.

Encoding · password-based key derivationSpec ↗
02 / BIP-32

Seed → HD key tree

HMAC-SHA512 creates a master extended private key and chain code. Child key derivation (CKD) yields reproducible descendants; hardened derivation prevents deriving those children from an extended public key.

Hierarchical key derivationSpec ↗
03 / BIP-44

Standardized wallet paths

Defines the account structure m / purpose' / coin_type' / account' / change / index. For a common Ethereum path the coin type is 60' (registered in SLIP-44).

Derivation-path conventionSpec ↗
04 / SECP256K1

Secret scalar → public point

For a valid private scalar k, the public key is Q = kG on the real 256-bit elliptic curve. The hard inverse problem is ECDLP; private keys sign transactions and public keys permit signature verification.

Public-key cryptography · signaturesGuide ↗
05 / KECCAK-256

Public key → address

Hash the 64-byte uncompressed public-key coordinates (without the 0x04 prefix). Take the final 20 bytes of the 32-byte Keccak-256 digest: the Ethereum address. Not the same as standardized SHA3-256.

Cryptographic hashing · truncationGuide ↗
06 / EIP-55

Address → mixed-case text

Apply case to address letters according to the Keccak-256 hash of the lowercase ASCII hex address. This adds error-detection information without changing the 20-byte address itself or hiding it.

04 / TWO HASH FUNCTIONS

Keccak-256 ≠ SHA3-256.

Same underlying Keccak-f permutation, different domain separation and padding. Compare real digests for the same input.

05 / HISTORICAL CONTEXT

A timeline of the primitives.

These mechanisms emerged at different times to solve different problems.

1977
RSA

Public-key cryptography enters mainstream research; one-way trapdoor mathematics enables encryption and signatures.

2001
SHA-2 (including SHA-512)

NIST standardizes SHA-2. SHA-512 is later used in HMAC and BIP-39/BIP-32 key derivation.

2012
BIP-32 · hierarchical deterministic wallets

Keys are derived from a single master secret through a reproducible key tree.

2013
BIP-39 · human-readable recovery mnemonics

Random wallet entropy gains a memorable encoded representation; PBKDF2 produces the seed.

2014
BIP-44 · wallet derivation paths

Standardizes purpose, coin type, account, change and address-index layout.

2015
NIST SHA-3 standard

Based on the Keccak construction but distinct from Ethereum's original Keccak-256 variant.

2016
EIP-55 · Ethereum checksum addresses

Mixed-case rendering adds limited error detection to hexadecimal Ethereum addresses.

06 / DISCUSSION & CONCLUSIONS

Why not one algorithm for everything?

01 / KEY MANAGEMENT

Generation and derivation are different.

Fresh wallet entropy is generated using a secure random source. BIP-39 encodes this randomness and derives a seed; BIP-32 deterministically derives many child keys. BIP-44 standardizes where those children reside.

02 / ASYMMETRIC CRYPTOGRAPHY

A public key is not a hash.

secp256k1 links the private scalar and public point through Q = kG. Security depends on the elliptic-curve discrete logarithm problem. It also enables the public/private-key relationship underlying digital signatures.

03 / HASHING

Keccak condenses data.

Keccak-256 turns a 64-byte public key into a fixed-length digest; the final 20 bytes identify an Ethereum externally owned account. Collision/preimage resistance and diffusion are hash-function concepts, not the same as ECDLP.

04 / CHECKSUMS & ENCODING

Capital letters detect mistakes.

EIP-55's casing is an error-detection checksum applied to a hexadecimal encoding. It is not a digital signature or encryption, and cannot guarantee all errors are caught.

FINAL TAKEAWAY

A secure wallet relies on composition: randomness and deterministic key management, asymmetric cryptography, cryptographic hashing, and human-readable error-detecting representation. Each primitive has its own mathematical goal and security assumptions.
